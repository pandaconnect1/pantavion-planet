# Pantavion HNCP Prior-Art Attack 4 — 2026-09-09

Status: RESEARCH / NOVELTY UNVERIFIED

## Purpose
Attack the current #1 candidate — Human Need-to-Capability Protocol (HNCP) — against adjacent prior art in capability contracts, intent-bound authorization, dynamic service composition, agent provenance and governed tool generation.

## Strong collisions found

1. Agent Capability Contract (ACC) already defines machine-readable agent-visible capability declarations with scope, risk, subject, approval, audit and execution metadata. Therefore Pantavion cannot claim novelty for a capability contract or risk/approval metadata alone.
2. Dynamic/context-aware service composition is old prior art. Research has long mapped user goals/context to runtime service composition. Therefore Pantavion cannot claim novelty for context -> service composition alone.
3. Tool Forge (2026) converts natural-language capability intent into governed, sandbox-verified, catalogued tools with contracts, tests, lifecycle state and routing metadata. Therefore intent -> generated tool + sandbox validation is not enough.
4. Intent provenance and deterministic authorization are rapidly becoming explicit standards/research areas in 2026: cryptographic intent chains, intent provenance protocols, deterministic action authorization and authority/inference separation. Therefore provenance + deterministic authorization alone is not enough.
5. Intent-adaptive smart services already combine predicted intent, policy constraints, atomic/composite services, dynamic workflow composition, resource allocation, trust/privacy and continuous adaptation. Therefore a broad 'intent + policy + composition + adaptation' claim is vulnerable.

## Required narrowing
The Pantavion candidate must NOT be framed as:
- an agent capability contract;
- an intent authorization protocol;
- a dynamic service composer;
- a tool generator;
- a personal/context-aware AI;
- a provenance ledger;
- a multi-agent orchestrator.

All of those have substantial prior art.

## Stronger surviving research hypothesis

### Human Need Transformation & Continuity Protocol (HNTCP)

The potentially differentiating object is not the capability and not the agent action. It is a **persistent, rights-bounded transformation of a human need across domains and time**.

Proposed chain:

`HUMAN_NEED`
`-> NEED_STATE (meaning, urgency, relationship role, accessibility, language, device, jurisdiction, consent)`
`-> ADMISSIBLE_OUTCOME_ENVELOPE (what outcomes are permitted/desired, not which tool to call)`
`-> CAPABILITY_PLAN (reuse/compose/create only inside envelope)`
`-> DETERMINISTIC_AUTHORITY_BOUNDARY`
`-> EXECUTION`
`-> OUTCOME_EVIDENCE`
`-> CONTINUITY_STATE (what remains unresolved, what changed, what must persist across thread/device/module/time)`
`-> NEXT NEED STATE`

### Research distinction to test
Most adjacent systems discovered in this pass focus on one or more of:
- exposing capabilities to agents;
- authorizing an action;
- composing services from context/intent;
- generating tools from natural language;
- proving delegation/action provenance.

HNTCP instead treats the **human need and its continuity** as the canonical control object. Capabilities, agents, tools, modules and providers are replaceable implementation resources beneath that object.

This is still NOT a novelty claim. It is the narrower hypothesis that now deserves the next prior-art/patent attack.

## Pantavion-specific recovered mechanisms that can strengthen the hypothesis

The hypothesis should be tested using recovered Pantavion mechanisms rather than generic AI vocabulary:
- one human identity with strict module boundaries;
- People/relationship graph distinct from Social;
- Chat originating from People/Social/consented contacts;
- scoped per-thread/per-user/per-module memory and continuity;
- language/interpreter lane preserving original and translated artifacts;
- deterministic age/consent/guardian/jurisdiction truth;
- SOS owning emergency truth rather than generic Chat/AI;
- low-data/offline/failover paths;
- device-adaptive execution;
- provider-neutral AI/tool routing;
- zero-loss provenance and explicit unresolved state;
- need-to-capability creation when an approved capability is missing.
